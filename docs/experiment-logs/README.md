# 실험 원시 로그 (2026-09-17)

논문 4장의 수치가 나온 원본이다. 표 2 는 아래 replay/ 의 재생 실험으로 대체되었다. 표의 숫자를 누가 물었을 때 여기서 다시 세어 보일 수 있다.

측정 환경은 로컬이며 운영 서버가 아니다. 단말은 실기기가 아니라 `tools/device-sim.sh`
시뮬레이터를 사용했다. 서버의 판정은 수신된 요청의 내용과 시각에만 의존하므로
동일한 요청을 동일한 간격으로 보내면 실기기와 구분되지 않는다.

서버 로그는 ANSI 색코드를 제거하고 판정에 관련된 줄만 남겼다. 원본은 각 70KB 내외였다.

## threshold/ — 임계값별 오탐과 감지 지연 (표 2, 최초 1회 측정)

**조건** 전송 주기 5초 · 유실률 40% · 150초 생존 후 완전 침묵 · 확인 주기 5초

임계값은 코드 상수(`Member.ONLINE_THRESHOLD_SECONDS`)라 조건마다 다시 빌드해 측정했다.
측정 후 값은 20초로 되돌렸다.

| 파일 | 내용 |
| --- | --- |
| `server-T{5,10,20,40}.log` | 서버가 남긴 단절 판정 기록 |
| `device-T{5,10,20,40}.log` | 시뮬레이터가 무엇을 보내고 무엇을 걸렀는지 |
| `results.txt` | 자동 집계 결과 |

### 숫자를 다시 세는 방법

단절 판정 횟수:

```bash
grep -c "기기 끊김 감지" server-T5.log
```

이 값에는 오탐과 참 감지가 함께 들어 있다. 둘을 가르는 기준은 **시뮬레이터의 전송 중단
시각**이다. `device-T5.log`의 `*** 전송 중단 ***` 줄보다 이른 판정은 단말이 살아 있는 동안
내려진 것이므로 오탐이고, 그 이후의 판정이 참 감지다.

감지 지연은 각 판정 줄에 함께 적힌 `마지막 수신` 시각과 판정 시각의 차이다.

### 조건별 내역

| 임계값 | 판정 총계 | 오탐 | 참 감지 | 감지 지연 |
| --- | --- | --- | --- | --- |
| 5초 | 6 | 5 | 1 | 7.5초 |
| 10초 | 3 | 3 | 0 ※ | 13.1초 ※ |
| 20초 | 1 | 0 | 1 | 22.5초 |
| 40초 | 1 | 0 | 1 | 43.3초 |

**T = 5초 상세** — 표 2에서 경계가 가장 깨끗한 조건이다. 마지막 성공 전송(15:12:41)과
전송 중단(15:12:46) 사이에 오탐이 끼지 않아 참 감지가 독립적으로 관측되었다.

| --- | --- | --- | --- |
| 15:10:53 | 15:10:46 | 6.7초 | 오탐 |
| 15:11:38 | 15:11:31 | 6.8초 | 오탐 |

**※ T = 10초의 예외** — 실제 단절 1초 전에 연속 누락으로 이미 판정이 내려져,
반복 억제가 작동해 참 단절에 대한 새 판정이 생성되지 않았다. 따라서 이 조건의
참 감지 지연은 정의되지 않으며, 위 표의 13.1초는 같은 구간에서 발생한 세 건의
판정 지연(12.7 / 13.0 / 13.7초) 평균이다. 논문 4.1에서 이 사례를 다룬다.

## replay/ — 수치 실험 시퀀스의 서버 재생 (표 2, 2026-10-18)

threshold/ 의 최초 측정은 조건당 1회라 통계적 근거가 부족하다는 심사 의견을 받았다.
같은 실험을 30번 반복하는 대신, **수치 실험(표 1)이 만든 유실 시퀀스를 서버에 그대로 재생해
시행마다 모형 예측과 서버 판정을 대조**했다. 확률 분포는 수치 실험 20,000회가 맡고,
재생 실험은 "서버 구현이 모형과 같은 판정을 내린다"를 입증하는 역할이다.

**조건** 표 1 의 앞 30개 시퀀스 · 단말 30대 동시 재생(조건마다 새로 등록) · 임계값 5/10/20/40초
· 전송은 시작 시각 + i×5초의 절대 시각 · 단말별 시작 위상을 5초 안에 고르게 분산 · 푸시 발송 끔

| 파일 | 내용 |
| --- | --- |
| `seqs.json` | 재생한 시퀀스와 시행별 모형 예측 (`paper-sim.py --export 30`) |
| `T{5,10,20,40}/sends.csv` | 재생기의 전송 기록. `STOP` 행이 실제 중단 시각 |
| `T{5,10,20,40}/members.json` | memberId → 단말 대응표. 서버 끊김 로그는 memberId 만 남긴다 |
| `T{5,10,20,40}/server.log` | 서버의 단절 판정 줄 |
| `results.md` | `tools/replay-compare.py` 대조 결과 |

```bash
tools/replay-run.sh 30                                      # 전체 재실행 (약 20분)
python3 tools/replay-compare.py docs/experiment-logs/replay/<실행시각>   # 대조만 다시
```

### 결과 (20261018-1851)

120회 중 118회가 오탐 건수·가림 여부·감지 지연 구간까지 모형과 일치했다. 전체 수치는 `results.md`.

**불일치 2회 (T = 10초 시행 4·7)** — 둘 다 서버 오탐이 모형보다 1건 적다. 정확히 2회 연속 누락된
구간(수신 간격 15초)에서, 스케줄러 확인 시각이 마지막 전송 후 +10.02초·+15.02초에 떨어졌다.
+10.02초 확인 시점에는 서버 수신 시각(전송 + 수 ms) 기준 경과가 아직 10초를 넘지 못했고,
+15.02초에는 다음 수신이 이미 도착해 있었다. 판정 창 (T, T+5] 와 확인 주기(5초 + 실행 시간)가
거의 같은 길이라 경계에 걸리면 한 주기를 건너뛴다. 모형은 확인 주기를 정확히 5초로 두므로
이 경우를 포함하지 않는다. 오탐이 줄어드는 방향이며 가림·지연 판정에는 영향이 없다.

## rollback/ — 트랜잭션 분리 대조 실험 (4.3절)

**조건** 알림을 저장한 직후 같은 트랜잭션에서 예외를 발생시키고 5회 반복

롤백은 실험용 코드를 넣어 만든 것이 아니다. 상태를 전이시키는 이벤트에 허용 범위를
벗어난 배터리 값(120)을 함께 보내면, 알림이 생성된 뒤 값 검증 단계에서 예외가 발생해
트랜잭션이 롤백된다. 기존 구현의 검증 순서에서 그대로 발생하는 경로다.

| 파일 | 구성 |
| --- | --- |
| `server-commit-after.log` | 커밋 이후 발송 (현재 구현) |
| `server-commit-before.log` | 커밋 이전 발송 (대조군) |

대조군은 `PushNotificationService`의 `@TransactionalEventListener(AFTER_COMMIT)`를
즉시 실행 리스너로 바꿔 만들었다. 측정 후 원복했다.

```bash
grep -c "notificationId:" server-commit-after.log    # 0
grep -c "notificationId:" server-commit-before.log   # 10
```

이 줄은 "등록된 기기가 없어 푸시를 건너뜁니다"라는 로그다. 로컬에 FCM 토큰이 등록되어
있지 않아 실제 발송 직전에 멈췄을 뿐, **푸시 발송 절차가 개시되었다는 증거**다.
대조군의 10건은 롤백 5회 × 수신자 2명이며, 해당 알림 식별자는 롤백되어
데이터베이스에 존재하지 않는다.

단절 감지를 구현한 직후 서버를 처음 기동했을 때의 기록이다.
논문 1장(서론)에서 인용한 관측 사례가 여기 있다.

```
기기 끊김 감지 - memberId: 1, deviceMac: AA:BB:CC:00:11:22,
                마지막 수신: 2026-08-21T03:34:34
```

기동 시각이 9월 17일이므로 마지막 수신으로부터 약 27일이 지난 상태였다.
그동안 대시보드에는 마지막 수신 당시의 상태가 그대로 표시되고 있었다.

**인용 시 주의** 이 레코드는 개발 데이터베이스의 것이며 운영 환경이 아니다.
논문에 쓸 때 그 점을 밝혀야 한다.

## 실험 재현

```bash
# 시뮬레이터는 feat/device-liveness 브랜치의 tools/device-sim.sh
./tools/device-sim.sh --device <등록된 device_mac> \
    --duration 215 --die-after 150 --loss 40
```

`--device` 값은 피보호자 등록 시의 `device_mac`과 문자열이 완전히 일치해야 한다.
다르면 서버가 404로 거부하며, 서버 로그의 "등록되지 않은 device_id" 줄에
서버가 받은 값이 남는다.
